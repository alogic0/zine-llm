# Markdown production validation

The pure-Zig Markdown and SuperMD pipeline has dedicated performance,
concurrency, robustness, workflow, and release gates. Run local commands from
the repository root through `build.sh` so they use the pinned Zig compiler.
Normal local validation builds and tests only the current host architecture.

## Performance and memory

```sh
./build.sh benchmark-markdown
```

The benchmark uses representative CommonMark, GFM, and SuperMD profiles. It
reports source bytes and these per-profile metrics:

- syntax parsing time;
- semantic total time and semantic overhead over syntax parsing;
- HTML rendering time;
- successful allocation count and total requested bytes;
- peak simultaneously live bytes.

The default is 50 iterations. Override it with
`-Dmarkdown-benchmark-iterations=N`. Timing results are intended for
same-machine before/after comparisons; they are not a portable pass/fail
threshold.

## Correctness and robustness

```sh
./build.sh test-markdown
./build.sh test-markdown-concurrency
./build.sh test-markdown-modes
./build.sh test-markdown-properties
./build.sh test
```

- The focused Markdown gate runs syntax, compatibility AST, semantic, backend,
  source-range, and allocation-failure tests.
- The concurrency gate repeatedly parses all benchmark profiles on eight
  threads with independent allocators. It compares semantic snapshot hashes
  and checks leak-free teardown.
- The mode gate runs Markdown and semantic tests in Debug, ReleaseSafe,
  ReleaseFast, and ReleaseSmall.
- The property gate parses generated byte sequences and truncations of
  malformed inline delimiters, links, images, tables, footnotes, directives,
  and fenced HTML. It renders syntax trees, validates all known byte ranges,
  and sends undefined-footnote and autolink cases through the same safety
  emitters used by the production renderer.
- The full gate runs unit tests, content scanning, page analysis, rendering,
  drafts, multilingual output, and committed snapshot comparisons.

## User workflows

```sh
./build.sh test-workflows
```

This creates a disk release in a build-owned output directory and verifies its
index page. The fixture includes production-rendered autolinks, resolved and
undefined footnotes, `$page.footnotes?()` output, and tight, loose, and nested
task lists. The gate also starts the development server, fetches a rendered
page over HTTP, verifies live-reload injection, and shuts the server down.

## CI and release validation

```sh
./build.sh test-release-tool-isolation
./build.sh check-release-targets -Dpreview=true
./build.sh release -Dpreview=true
./build.sh verify-release -Dpreview=true
```

These all-target commands belong to GitHub CI and release automation; normal
local development does not require them. Pushes to `main` run the compile-only
and archive-tool-isolation gates. Version tags and manual CI dispatches build
and verify the release archives.

The archive-tool isolation gate removes `tar`, `gtar`, `zip`, and `xz` from
`PATH`; it proves that `check`, `test`, and `check-release-targets` still pass
and that only `release` reports a missing packaging command. The compile-only
gate checks all supported release triples without creating archives. The
release gate additionally packages them. `verify-release` requires exactly
eight archives and checks each one for `zine` or `zine.exe` as appropriate.
`-Dpreview=true` is required while the repository version contains `-dev`.

Supported triples are:

- `aarch64-macos` and `x86_64-macos`;
- `aarch64-linux-musl` and `x86_64-linux-musl`;
- `aarch64-freebsd.15.0` and `x86_64-freebsd.15.0`;
- `aarch64-windows` and `x86_64-windows`.
